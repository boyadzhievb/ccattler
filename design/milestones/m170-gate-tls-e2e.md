# M170 — Gate TLS End-to-End Validation

Validate M169 gate TLS termination on a real cluster. M169 shipped with unit and
API tests only (parser, compiler, `RouteTLSController`, cookie proxy TLS, agent
dataplane config); no traffic has crossed a TLS gate on real nodes.

## Findings From Planning (fix before e2e)

Code reading while writing this plan found gaps the unit tests do not cover:

| # | Finding | Evidence | Plan |
|---|---------|----------|------|
| F1 | **TLS-only gates are never dispatched to the TLS proxy (nftables).** `buildRouteDispatchOverrides` skips routes with `StickyMethod == ""`, so a gate with `tls` but no `sticky` gets its `rt_*` chain but the VIP dispatch never jumps to it. | `network/nftables_dataplane.go:138` | Fix: include routes with TLS material. Unit test: TLS-only route produces a dispatch override. |
| F2 | **iptables handles TLS-only gates** (`case StickyMethod == "cookie" \|\| hasTLS`, no sticky filter), but no test covers it. | `network/iptables_dataplane.go:124` | Add a unit test so it can't regress like nftables. |
| F3 | **eBPF data plane ignores TLS.** Its `ReconcileRouteDataPlane` only enables source-IP affinity. | `network/ebpf_dataplane.go:484` | Out of scope for M170 (eBPF route work belongs to M184). Agent logs a warning when a TLS gate exists under `--dataplane ebpf`; documented in `design/dsl-reference.md`. |
| F4 | **A TLS gate takes over the whole service VIP:port.** The override is keyed by VIP:port, so in-cluster clients calling that service over plain HTTP on the same port will hit the TLS listener. Same mechanism as cookie-sticky today. | `buildRouteDispatchOverrides` | Decision needed (see below). M170 tests the chosen behaviour explicitly. |
| F5 | **External traffic on the deploy env goes through Caddy on testbed-100.43**, which proxies straight to backends from route facts and bypasses the gate data plane. | `scripts/caddy-sync.sh` | M170 tests at the VIP from cluster nodes. Caddy TLS passthrough is out of scope. |

### Decision: F4

- **Option A (recommended for M170):** accept and document: a gate with `tls` makes that service port HTTPS for every client. In-cluster callers use `https://` with the cluster CA. Simplest; matches existing cookie-sticky semantics.
- **Option B:** gates get their own listen port (e.g. VIP:443) and leave the service port untouched. Cleaner semantics but a data plane change; would become its own milestone.

## Environment

- Deploy cluster on testbed-100.43 (vmherd): ctrl `192.168.124.10`, workers `.20` / `.30`; nftables data plane.
- Run via `test/e2e/cluster_test.sh --env deploy --workload gate-tls` (same harness as whoami/airflow).
- Cluster CA certificate: `/etc/ccattler/ca.pem` on every node (written by `cca init`), used as `curl --cacert`.
- All HTTPS checks run from cluster nodes against the service VIP with `--resolve <host>:<port>:<vip>` so SNI/Host match the gate host.

## Test Workload

New `test/e2e/workloads/gate-tls.cca` + `gate-tls.workload`. One service per gate, because overrides are keyed by VIP:port:

| Service (whoami, 2 instances) | Gate | TLS | Sticky |
|---|---|---|---|
| `tls-auto` | `tls-auto.home.arpa` | `tls auto` | — |
| `tls-manual` | `tls-manual.home.arpa` | `tls { cert key }` | — |
| `tls-sticky` | `tls-sticky.home.arpa` | `tls auto` | `cookie` |

The manual cert/key pair is generated by the test with `openssl` (self-signed, SAN = gate host) next to the `.cca` file before apply, never committed.

## Test Cases

| ID | Case | Pass criteria |
|----|------|---------------|
| T1 | Auto issuance | Within 60 s of apply, `cca get gates` shows `tls-auto` and `tls-sticky` as `auto` with an EXPIRES date ~90 days out; no `(pending)`. |
| T2 | HTTPS via VIP (auto) | `curl --cacert ca.pem https://tls-auto.home.arpa` from each node returns 200 with whoami body. |
| T3 | Certificate identity | `openssl s_client` shows SAN = gate host, issuer = cluster CA; matches `cca describe gate` Host/Expires. |
| T4 | Manual cert served | Served cert fingerprint equals the generated cert's fingerprint. |
| T5 | Manual rotation | Regenerate cert, re-apply; new fingerprint served within 30 s; no failed requests in a 1 req/s loop during the switch. |
| T6 | Round-robin (TLS-only) | 20 HTTPS requests to `tls-auto` reach both instances (whoami `Hostname`). Covers F1. |
| T7 | Sticky + TLS | First HTTPS response sets the sticky cookie (Secure); 10 requests with the cookie hit one instance. |
| T8 | Cert stability | Restart `cca server` and one agent; fingerprint unchanged (no re-issue churn), traffic recovers. |
| T9 | Backend failure | Kill one `tls-auto` instance; HTTPS keeps succeeding within the health-check window. |
| T10 | TLS removal | Remove `tls` from `tls-auto`, re-apply; derived TLS facts deleted, plain HTTP works on the VIP. |
| T11 | No key leakage | `cca get gates -o json`, `cca describe gate` contain no `BEGIN`; agent logs contain no PEM. |
| T12 | VIP takeover (F4) | Plain `http://` to `tls-auto` VIP:port fails with a TLS error (Option A), documented as expected. |

Renewal-window logic (re-issue 30 days before expiry) stays covered by `controllers/route_tls_test.go`; waiting 60 days is not practical in e2e.

## Phases

1. **Fixes** — F1, F2, F3 warning, with unit tests.
2. **Workload + harness** — `gate-tls` workload, cert generation, T1–T12 checks in `cluster_test.sh` (inside retry/wait loops, per the `waitFor` rule).
3. **Run & fix** — run on the deploy cluster until green on 3 consecutive runs.
4. **CI + docs** — add `gate-tls` to the deploy-testbed workflow default list; document F3/F4 behaviour in `design/dsl-reference.md` and `design/gate-tls-termination.md`.

## Out of Scope

- eBPF TLS support (M184), separate gate listen port (Option B), Caddy TLS passthrough, ACME.
